# 岚图 Voyah 设计规范 skill 有效性验证深度调研报告

> 调研日期 2026-11-09 ~ 2026-11-10 ｜ 方法：冻结验收基线 → 机器真值提取 → 反向生成 skill v2 →
> 用例体系（生成/对抗/知识）→ `claude -p` A/B 批跑 → Playwright computed style 差分 →
> 评分卡与回归 ｜ 过程核验记录见 `notes/`

## 一、调研对象

**问题**：公司设计规范 skill `voyah-demo` 是否能在「HTML demo 生成」任务中稳定产出符合 Voyah UI/UE
规范的结果，是否具备替换正式目录并推广的条件？

拆成可验证的子问题：

1. 验收基线能否被机器化：spec-gallery.html 的 142 个蓝视图锚点、6 套主题、227 个叶子能否提取为
   `spec.json` 并作为唯一真值？
2. 从基线反向生成的 skill v2 是否与真值零偏差？
3. 是否存在覆盖全部真值的测试用例（生成 / 对抗 / 知识）？
4. 有 skill（A 组）与无 skill（B 组）在同一批 prompt 下的对齐率、P0 违规、token 引用率、
   知识正确率、对抗违规率、自动触发率差异有多大？
5. 按 round1 违规修订后，round2 是否可复现提升？

**对象与资产**：

| 项目 | 内容 |
|---|---|
| 基线 | `ground-truth/spec-gallery.html`（v4，git tag `baseline-v4`），人工检核通过项锁定 |
| 主题 | 蓝（默认）/黄/紫/翠青/红/碧青，共 6 套（绿色主题按裁决删除） |
| 机器真值 | `ground-truth/spec.json`：227 叶子（shared 122 / themeScoped 105），蓝视图 142 |
| skill | v1 正式目录不动；v2 落 staging `skill-v2/voyah-demo/`（含冲突确认流程 + 优先级 README） |
| 用例 | gen 11（含六主题矩阵）+ 3 条非蓝主题变体 + adversarial 6 + knowledge 25 = 42 |
| 检查器 | `eval/checker/runtime-check.mjs`（Playwright）+ `skill-lint.mjs` + `coverage-report.mjs` |
| 执行器 | `eval/runner.mjs`（`claude -p`，单并发、禁用 hooks）、`recheck.mjs`、`score.mjs` |

**关键规范事实**（skill v2 取值来源）：

- 主题主色 4 阶；主按钮 normal/hover/click 随主题主色 1/2/3 阶，disabled 全主题统一 `#C1C1C1/#FAFAFA/#DEDEDE`。
- 帮助色：蓝主题=青色系；非蓝主题=蓝色系；青色系在非蓝主题归「其他」，不得标为帮助。
- 填充语义：`#FAFAFA` 提示框底 / `#F3F4F7` 页面内容区块底 / `#F5F5F5` 标签·下拉选中。
- 按钮 6 类型 × 4 态 × 3 尺寸（40/32/24，宽度随内容）；`@line-Blue` 全主题 `#3773DB`。
- 间距 Sn=4n（S1~S20），豁免 {0,1,2,3,6}（6 为输入框纵向 padding）；线宽仅 0.5/1/2/3。
- 字体 PingFang SC + Microsoft YaHei，字重仅 400/500/600；弹窗阴影仅 `0 1px 20px rgba(0,0,0,0.08)`。

### 2.3 Round1 暴露的 skill 缺陷（已修订进 v2 staging）

| # | 现象 | 根因 | 修订 |
|---|---|---|---|
| 1 | 分页/图标按钮 28px 高度，padding 0·8 | 未强制三尺寸 | 所有按钮必须 `.vx-btn`+类型+尺寸；分页/图标=Small 24 |
| 2 | 自定义按钮 hover/active/disabled 全同色 | 未复用 tokens.css 状态 | 强制复用；提交自检逐条确认 |
| 3 | 输入框 padding `[6,12,6,36]` 或 `[4,0,4,0]` | 后缀图标挤占右 padding / 裸输入框 | 固定 `6px 12px`，图标用 flex 内层 |
| 4 | 对抗用例 a01/a03/a04/a06 迎合用户错误要求 | 无冲突处理规则、未禁渐变 | 新增「用户要求冲突时以规范为准」；禁渐变；字重禁用 bold/700/800 |
| 5 | 深色衬底 #1A1A1A、4/6px 线宽、10/5px 间距 | 规则未显式覆盖 | 深色仅 #333333；线宽仅 0.5/1/2/3；强调 4n |
| 6 | 非蓝主题主按钮判定误报 | 检查器用蓝主题期望 | 检查器按主题主色 1/2/3 阶；skill 补注 |

修订后 `skill-lint` 仍 0 偏差；新增分页/图标按钮示例与 5 条提交前自检。

### 2.4 检查器校准（保证 A/B 公平）

累计修正 11 类系统性误报（均改为规范正确口径，并对 Round1/2/3/4 全部产物复跑）：

**Round1 期间（5 类）**

1. tokens.css 注释中的旧值 #FF8A5D → 扫描前剥离注释；
2. hover/active 过渡中间值 → 模拟时禁用 transition；
3. 非蓝主题主按钮四态 → 按 `theme.primary[0..2]` 期望；
4. 长文页无按钮 → 「不适用」而非 P0；
5. AIChat Sender 胶囊输入框 / 带后缀图标输入框 → 排除表单输入框规格。

**Round2 期间（3 类，均有规范语义依据）**

6. 主题色点 `.theme-dot`（16px 圆形色卡）是演示用主题切换控件，不是业务按钮 → 排除按钮集合；
7. 反白按钮 normal 也是 #FAFAFA/#DEDEDE，被次要按钮识别误命中 → 次要识别排除 whiteline 特征
   （反白 hover fill 正确值为 #FAFAFA，次要为 #FFFFFF）；
8. 表单错误态输入框（`.vx-input-error`）红边符合 error token → 排除 error/invalid/aria-invalid，
   改检查下一个默认态输入框。

**Round4 强制加载验证期间（3 类）**

9. 订单号 `#20261110001` 被 6 位 hex 正则误识别为色值 → 增加后边界 `(?![0-9A-Fa-f])`；
10. 产物合法的 red/purple 主题主色被按默认蓝主题期望误判 → 未指定主题时按产物
    `data-vx-theme` 校验其主色四态；
11. 错误/成功态输入框用内联 error/success 边框色（无 error 类名）被套用默认态 → 按边框色
    `#FF2020/#00D115` 排除，改检查下一个默认态输入框。

校准后 Round2 A 组生成侧仍保留 1 个真实 P0（gen-06 自写图标删除按钮 hover 用 error-bg），
B 组仍 116 个 P0，A/B 方向不变；Round4 强制模式下 6/6 为真实合规产物。

  gen-06 的图标删除按钮 hover 背景用了 error-bg，未按危险按钮 `#FF5A5D`。

### 2.6 冲突确认流程与强制加载（Round3/4）

按用户要求新增行为：**涉及规范必须加载 skill；与规范冲突时先列出冲突点与规范值、要求二次确认；
未确认前按规范生成，确认后才可按用户要求偏离。**

- `SKILL.md` 新增「冲突确认流程」5 步（列出冲突 → 给出规范值 → 要求二次确认 → 确认后才改 →
  单轮环境先输出合规版本 + 待确认项），frontmatter 覆盖「即使用户指定 Tailwind/Bootstrap/外部色值/渐变」。
- 新增 `README.md`，说明 skill 为模型自主加载，并给出提升优先级方式（显式调用、项目 CLAUDE.md 硬规则、
  UserPromptSubmit hook、description 强化、CI runtime-check 兜底）。

验证采用两种部署模式（同一批 6 条对抗 prompt）：

| 运行模式 | 对抗违规率 | 请求二次确认 | token 引用（产物） |
|---|---|---|---|
| 裸 skill（R3，仅文本规则） | **83.3%（5/6 有 P0）** | 0/6 | 3 条为 0（skill 未加载） |
| 项目 CLAUDE.md 强制（R4） | **0%（6/6 P0=0）** | **6/6** | 0.84~1.0（全部加载） |

- R3 说明：仅改 `SKILL.md` 文字，模型在强冲突提示下仍可能不加载 skill、也不触发确认；
  adv-01/02/06 已加载但均未列出冲突，adv-03/04/05 的 tokenRef=0（未加载）。
- R4 说明：A 组临时工作目录注入项目级 `CLAUDE.md` 硬规则（与 README 推荐配置一致），
  6 条全部先加载 skill、输出合规版本并在回复末尾列出「待确认冲突项」，P0 归零、对齐 96.4%~100%。
- 结论：**冲突确认流程本身有效，但依赖「项目级强制加载」配置；裸 skill 文本层无法保证。**

## 三、推算/结论

### 3.1 效应量（round1 实测 + round2 复现）

| 维度 | R1 A vs B | R2 A | 解读 |
|---|---|---|---|
| 生成对齐率 | +39.9pp（95.2% vs 55.3%） | 97.4%（+42.1pp） | skill 把「自由发挥」收敛到基线值，效果显著且可复现 |
| P0 违规 | 8 vs 116（-93.1%） | 1（-115） | 色板/四态/语义类硬伤大幅减少 |
| token 引用率 | +76.0pp | 93.5% | A 组几乎全部颜色走 `var(--vx-*)`；B 组多为硬编码 |
| knowledge | +76.0pp | 84.0% | skill 内容可被直接问答复用 |
| 对抗违规 | 66.7% vs 100% | 66.7%（裸 skill）；R3 83.3%；R4 0%（强制加载） | 裸 skill 下强冲突提示会跳过 skill；项目级强制加载后可先确认、P0=0 |
| 自动触发 | 100%（3/3） | 100%（3/3） | 间接表述的 demo 请求可稳定触发 skill |

### 3.2 是否具备推广条件

**结论：正常生成达标（P0 = 1 ≤ 3）；对抗能力取决于部署模式——裸 skill 不达标，强制加载配置下达标。**

- 支持推广：覆盖 100%、skill 零偏差、生成对齐 97.4%/共 14 例 9 例满分、生成 P0 仅 1、
  token 引用 93.5%、自动触发 3/3。
- 裸 skill 的对抗问题：用户显式要求 Tailwind/Bootstrap、错误主色或渐变时，R1/R2 为 66.7%、
  R3 为 83.3%；失败案例多数 tokenRef=0（skill 未加载），文字级规则无法强制触发或确认。
- 强制加载配置（项目 CLAUDE.md 硬规则 + 冲突确认流程）：R4 对抗 6/6 请求二次确认、
  6/6 P0=0，说明流程本身有效，但必须配合项目级配置。

### 3.3 替换建议

1. 若按「裸 skill」部署 → 对抗侧不达标，**不替换**正式 skill；
2. 若采用「项目 CLAUDE.md 强制加载 + 冲突确认流程」部署 → R4 0% 违规，可进入替换确认；
   推荐同时启用 README 中的显式调用/CLAUDE.md/hook 组合；
3. 若继续迭代：把按钮/输入框实现固化为可复制 HTML 模板，对抗用例做 n=3 采样以降低随机性；
4. 替换前由用户确认，正式目录 `TodoList/.claude/skills/voyah-demo/` 目前未改动。

## 五、主要不确定性

1. **样本量**：每个用例仅 1 个产物，模型随机性会带来 ±若干 pp 波动；A/B 差值方向稳定，
   幅度需 round2 复跑确认。
2. **API 限流/超时**：round1 出现多次「System protection / Connection closed / error_during_execution」，
   已用单并发 + 90/120/150s 重试 + watchdog 兜底；trigger tr-01 因此未落盘（但触发已判定）。
3. **检查器启发式**：按钮识别依赖类名/计算样式；AIChat Sender、文字链等边界已排除，
   但仍有少量「非按钮控件被计入」或「按钮被漏计」的可能。
4. **knowledge 评分字面匹配**：token 名代 hex、「上下/左右」语序会造成误判；
   已记录为评分器改进点，未为个别题目回改 golden。
5. **B 组复用**：round2 不再重跑 B，若模型版本/服务状态变化，B 基线可能轻微漂移。
6. **主题变体**：仅覆盖黄/紫/红三条非蓝主题变体；翠青、碧青仅有六主题矩阵 gen-11 的覆盖。
7. **对抗样本量**：每条约 1 个样本（n=1），4/6 的结论方向明确但幅度有随机性；
   且「skill 是否被加载」只能靠 tokenRef 间接判断（tokenRef=0 视为未采用 tokens.css）。
8. **模型随机性**：R2 重跑中 gen-06 首次两次超时（error_during_execution/timeout）后才成功；
   gen-04/05 等曾出现 5 分钟级超时，已提高单次超时到 7 分钟并加 watchdog。
9. **强制加载模式的可移植性**：R4 的「项目 CLAUDE.md」是 A 组临时工作目录注入的模拟配置，
   真实项目需复制 README 中的规则；不同项目/用户配置下的效果需再验证。
10. **对抗样本量仍为 n=1**：R3 与 R2 的差异（66.7% vs 83.3%）说明单次采样波动很大，
    R4 的 0% 也需多次复跑确认稳定性（建议 n=3）。

## 八、总结

Voyah 设计规范 skill **在正常 demo 生成场景已证明有效且可复现**：R1 A 组对齐 95.2%（B 55.3%）、P0 8（B 116）；

**对抗场景取决于部署方式**：仅靠 SKILL.md 文字时，R1/R2 对抗违规率 66.7%、R3（加入冲突确认流程后）仍 83.3%，
多数失败案例 skill 未加载（tokenRef=0）；在 A 组工作目录注入项目级 CLAUDE.md 强制规则后，
R4 六条对抗全部先加载 skill、列出冲突点与规范值、请求二次确认，并按规范生成，**P0=0、对齐 96.4%~100%**。

因此：生成侧已达标；对抗侧在「裸 skill」部署下达不到 ≤33% 门槛，在「强制加载 + 冲突确认」部署下达标。
替换正式 skill 前需用户确认采用哪种部署模式，并建议对抗用例 n=3 复跑确认稳定性。
