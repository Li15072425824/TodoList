# 核验：冲突确认流程与 skill 强制加载（Round3/4）

## 被核验主张

1. 仅修改 SKILL.md，把「冲突一律以规范为准」改为「列出冲突 → 给出规范值 → 要求二次确认」
   即可让模型在冲突时先确认。
2. 在项目级 CLAUDE.md 强制「生成前必须加载 voyah-demo skill」后，同一批对抗用例可做到
   先确认、不静默服从，对抗 P0 归零。

## 核验过程

- 修改 `skill-v2/voyah-demo/SKILL.md`：
  - frontmatter 覆盖「用户指定 Tailwind/Bootstrap/外部色值/渐变」场景；
  - 新增「冲突确认流程」5 步；
  - 原硬性规则「一律以规范为准」改为引用该流程。
- 新增 `skill-v2/voyah-demo/README.md`，说明 skill 为模型自主加载，及提升优先级的 5 种方式。
- Round3（裸 skill）：只跑 6 条对抗，`--round=3 --cases=adv-* --skip-knowledge --skip-trigger`。
  - 结果：5/6 有 P0（83.3%）；0/6 在回复中列出冲突或请求确认；
  - adv-03/04/05 产物 tokenRef=0（skill 未加载）；adv-01 已加载（tokenRef 0.867）但仍直接使用用户红色。
- Round4（强制加载）：A 组临时目录注入 CLAUDE.md（内容为 README 推荐规则），同一批 6 条对抗。
  - 结果：6/6 请求二次确认、6/6 P0=0；对齐 96.4%~100%；tokenRef 0.842~1.0；
  - 产物均为「按规范生成的版本 + 待确认冲突项」；无一条按用户错误要求落地。
- 检查器追加 3 类校准：
  1. 订单号 `#20261110001` 被 hex 正则误判 → 加后边界；
  2. 合法 red/purple 主题被按蓝主题主色期望误判 → 按产物 `data-vx-theme` 校验；
  3. 无 error 类名的红/绿边框输入框（错误/成功态）被套默认态 → 按边框语义色排除。

## 结论

1. 主张 1 **否决**：裸 skill 下 0/6 请求确认、5/6 仍有 P0；SKILL.md 文字无法保证加载或确认。
2. 主张 2 **成立（限本次单轮样本）**：强制加载配置下 6/6 确认、P0=0；但为 n=1，且依赖项目级配置，
   需在真实项目复验并建议 n=3。
3. 关键机制：冲突确认规则只有在 skill 被加载后才可见；要让「涉及规范必加载」，必须用
   CLAUDE.md / hook / 显式调用等 skill 之外的强制手段（见 README）。
